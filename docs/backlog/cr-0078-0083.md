# Review backlog: CR-0078 through CR-0083

Items surfaced during CR review that would ordinarily need an author decision. Each was
decided on the most conservative reading consistent with the codebase as it stands, and is
recorded here with the chosen reading so it can be overturned on the record rather than
rediscovered in a diff.

## CR-0078: Email Management Write Verbs for Received Mail

* **Scope of the shared-parameter check (FR-16).** The requirement was written
  domain-agnostically while In Scope, Technical Impact, and Phase 4 all committed to two
  `list_messages` rewrites. Enumerating the registry showed a domain-agnostic check selects
  three further mail parameters (`message_id`, `importance`, `account`) and ten calendar
  parameters (`account`, `calendar_id`, `categories`, `end_datetime`, `event_id`,
  `importance`, `is_all_day`, `sensitivity`, `show_as`, `start_datetime`).
  **Chosen reading:** scope FR-16 and its check to the `mail` domain, exempt `account`
  explicitly in the requirement, and relax the assertion from "names each declaring write
  verb" to "names at least one declaring write verb" so a shared identifier parameter does
  not have to enumerate eight verbs in the published schema.
* **Two pre-existing description rewrites pulled into scope.** `message_id` (published from
  `get_message` as "The unique identifier of the message to retrieve.") and `importance`
  (published from `list_messages` as "Filter by message importance.") are pre-existing
  instances of exactly the defect FR-16 describes. **Chosen reading:** rewrite them in this
  change, taking the rewrite count from two to four, because a check that derives its cases
  from the registry fails on arrival otherwise, and carrying an exclusion list is the
  instance-level remedy `CLAUDE.md` already records as not closing a class. Cost is two
  additional lines in `internal/server/mail_verbs.go`.
* **Extending the shared-parameter check to every domain is deferred.** The calendar domain
  has ten shared parameters whose rewrites would exceed this change in size.
  **Chosen reading:** out of scope here, recorded as follow-on work in Phase 4 step 6 and
  in Open Question 7. A future change request should make the check domain-agnostic and
  land the calendar description rewrites with it.
* **`ParseFlagStatus` default on an unrecognised value.** The helper it mirrors
  (`ParseImportance`) silently defaults rather than returning an error, and for a flag the
  natural default (`notFlagged`) *clears* the flag instead of leaving it unchanged.
  **Chosen reading:** keep the existing helper shape rather than introduce a second
  convention, state the default in the doc comment, and require both
  `validate.ValidateFlagStatus` and the schema enum as gates before the parser can be
  reached.
* **Formatter file placement.** `CLAUDE.md` names `internal/tools/text_format.go` as the
  home for text formatters, but `FormatDraftConfirmation` already lives in
  `draft_helpers.go`. **Chosen reading:** follow the existing exception rather than invent
  a new one, and state the precedent in Affected Components so the deviation is on the
  record.
* **Signature of the shared confirmation formatter (Phase 1 step 3).** The CR names the
  fields the formatter renders but not its signature. **Chosen reading:**
  `FormatMailWriteConfirmation(action, subject, messageID, field, value, consequence string) string`,
  rendering `Message <action>: "<subject>"` / `ID: <id>` / `<field>: <value>` plus the
  consequence line when non-empty. One `field`/`value` pair rather than a map or a variadic
  keeps the three property writes and the move on one shape (each changes exactly one field),
  and the line ordering mirrors `FormatWriteConfirmation`, which the calendar write verbs
  already publish. A verb needing two changed fields would extend the signature rather than
  be served by a second formatter.
* **Reporting a field the Graph response omits (FR-13, Phase 2).** FR-13 requires the
  confirmation to be built from the response, but a response that omits the written field
  leaves nothing to report, and falling back to the request argument would state as applied
  a value never confirmed. **Chosen reading:** report
  `unknown (not reported by Graph)` for the flag status and the read state, so the absence
  is itself visible rather than papered over with the requested value.
* **A missing `categories` value is not a clear instruction (FR-8, Phase 2).** FR-8 makes an
  empty or whitespace-only value clear every category, which leaves the omitted-parameter
  case undecided. **Chosen reading:** `categories` is required, and its omission is refused
  by name; clearing must be asked for with an explicit empty string, so a dropped argument
  cannot silently wipe a label set.
* **Rendering the cleared state (FR-8, Phase 2).** **Chosen reading:** the `Categories`
  value reads `none` and the formatter's consequence line carries
  `The message now carries no categories.`, which keeps the shared four-line shape rather
  than special-casing the formatter, and satisfies the requirement not to print an empty
  list.
* **Invalid-identifier test input (Phase 2 tests).** `validate.ValidateResourceID` bounds
  emptiness and length only; it does not reject a character set. **Chosen reading:** the
  before-the-call rejection is exercised with an over-length identifier, and the test says
  why, so a later reader does not take a passing "malformed identifier" case as evidence of
  character-set validation the helper does not perform.
* **The move body is serialised as `DestinationId`, capitalised (Phase 3).** The Graph
  reference documents the action parameter as `destinationId`, and the first wire assertion
  was written against that spelling and failed. Reading the pinned SDK's generated
  serializer (`users/item_messages_item_move_post_request_body.go:77` in
  `msgraph-sdk-go@v1.100.0`) shows it writes `DestinationId` while storing under
  `destinationId` in its backing store. **Chosen reading:** assert what the SDK actually
  puts on the wire and state in the test why the documented spelling is not the one
  asserted, rather than reshape the call to produce the documented casing.
* **Which identifier the move confirmation puts on the `ID:` line (FR-4, Phase 3).** The
  formatter renders one identifier there, and the move has three to report.
  **Chosen reading:** the `ID:` line carries the **new** identifier, because that is the
  only one that still resolves; `Destination folder` carries the destination; and the
  consequence line names the original identifier and states that it no longer resolves. All
  three are present, and the one a caller should use next is the one in the position every
  other mail write verb puts a usable identifier in.
* **Cross-handler assertions are table-driven over the four verbs (Phase 3).**
  `mail_write_verbs_test.go` enumerates the family in one table and asserts the family-wide
  properties (one Graph request on success, `message_id` required, the no-account refusal,
  subject and identifier read from the response, the no-subject placeholder, and a fix
  instruction on Graph failure) over every row. **Chosen reading:** a fifth verb of this
  shape is covered by adding a row rather than by remembering to repeat six tests, which is
  the derive-the-cases remedy `CLAUDE.md` prefers over per-instance coverage. The
  idempotence assertion (NFR-8) skips `move_message` by name, since it mints a new
  identifier per call and is classified non-idempotent for that reason.
* **Landing-order dependency on absolute surface figures.** CR-0079 through CR-0083 each
  state absolute surface counts against the same 42-verb baseline. **Chosen reading:** the
  regenerated `site/src/generated/surface.json` and `TestCommittedManifestMatchesRecord`
  are authoritative; whichever change request lands second amends its own figures rather
  than the manifest.
* **Phase 4 lands with two generated artefacts deliberately stale.** Registering the four
  verbs makes `TestVerbInventoryUnchangedAfterUpgrade` (FR-23) and
  `TestCommittedManifestMatchesRecord` (FR-21) fail, because both compare a committed
  generated record against the live registry. Both regenerations are Phase 5 steps 7 and 4.
  **Chosen reading:** leave them failing at the Phase 4 checkpoint rather than pull Phase 5
  forward. The verb-inventory delta was inspected and is exactly the four expected lines
  with the hints the annotation matrix specifies, so the failure is the check reporting the
  intended change rather than a defect. Phase 5 closes both.
* **How the shared-parameter check reads a verb's read or write sense (Phase 4 step 6).**
  The registry stores `readOnlyHint` as an opaque `mcp.ToolOption`, not as a field.
  **Chosen reading:** materialise each verb's `Annotations` and `Schema` into a throwaway
  `mcp.NewTool` and read the resulting hint and properties back, which is the same path
  `aggregateSchemaOptions` takes to publish them. Deriving the verb's classification from
  its name, or from the gate it sits behind, would let a mis-declared hint pass the check.
  The check was falsified by substitution before being trusted: reverting the `flag_status`
  description to its pre-change text fails the test naming the parameter, the declaring
  read verb, and the declaring write verb.
* **`internal/docs/catalog_test.go` touched in Phase 5 despite not being listed among its
  affected components.** The Test Strategy names `TestMailGatingRowNamesMessageManagement`
  in that file as the gate on FR-24, and Phase 5 is the only phase that edits
  `docs/concepts.md`; no earlier phase claimed the file, and it did not exist at the end of
  Phase 4. **Chosen reading:** add the test in Phase 5 and record the one-file scope
  expansion here rather than land FR-24 with no gate. The CR's Phase 5 affected-components
  list is the entry that is wrong, not the test table.
* **Numbering of the new lifecycle steps (FR-22).** The existing skip instruction covers a
  contiguous range, "Steps 31 through 35", but Step 36 (`get_attachment`) is
  `MailEnabled`-gated rather than `MailManageEnabled`-gated, so the new steps cannot be
  appended contiguously to the gated range without renumbering Step 36. **Chosen reading:**
  append the four steps as 37 through 40 and widen the instruction to two ranges, since
  renumbering an existing step would silently invalidate every historical run's step
  references in `docs/bench/crud-runs.csv`.
* **Steps 37 through 39 write to a real received message and restore it; Step 40 does not
  move one.** The move mints a new identifier and the original stops resolving, which is
  not restorable, so the move step creates its own disposable draft as the subject and
  deletes it afterwards. The three property writes are reversible, so they act on a real
  Inbox message and each step ends by restoring the value it recorded first.
* **The live-mailbox acceptance run is outstanding, and is the user's to make.** The CR's
  Verification Commands section requires a user scenario driving the built server against a
  live mailbox, plus a `make crud-test` run. Both need an authenticated mailbox and a paid
  harness run, so neither was performed. The scenario has been derived and persisted at
  `.agents/scenarios/2026-09-01-received-message-management-lifecycle.md`, marked
  `outcome: not-run` in its own frontmatter, so the run can be performed without
  re-deriving it. **Chosen reading:** land the implementation with the scenario written but
  unrun, and name the run here as pending rather than record an unperformed run as
  evidence. Until it happens, no evidence exists that any of the four verbs has issued a
  real Graph call: every passing test drives an `httptest` server with canned JSON. Whoever
  runs it rewrites the artifact's `outcome` and `runs` fields and appends the run log, and
  checks the harness report's own server version line against `git rev-parse --short HEAD`
  before trusting a row of it.

* Pre-existing drift found by the doc updater, outside CR-0078 scope: `docs/concepts.md` `MAIL_ENABLED` row lists `mail.get_attachment` but omits `get_conversation` and `list_attachments`, and lists `get_message`/`search_messages` which are always-on. Fix together after the CR set lands.
* Pre-existing drift found by the doc updater, outside CR-0078 scope: `extension/README.md` names only `Mail.Read` and does not mention `Mail.ReadWrite` under `MAIL_MANAGE_ENABLED`, same class as the `extension/manifest.json` `long_description` defect the CR holds out of scope.

## CR-0079: Mail Draft Attachments

Reviewed against `ee23a77`, after CR-0078 landed. The CR was authored at `78a3bb3`, so
every path, line number, symbol, and count it cited was re-verified first. Ten drift
findings, three contradictions, seven ambiguities, four coverage gaps, and four scope
inconsistencies were fixed in the CR itself. The items below are the ones that would
ordinarily have needed the author, each decided on the most conservative reading
consistent with the codebase and recorded here so it can be overturned on the record.

* **Open Question 1, a distinct upload bound versus reuse of `MaxAttachmentSizeBytes`.**
  The CR proposed a distinct `OUTLOOK_MCP_MAX_ATTACHMENT_UPLOAD_BYTES` on the ground that
  the download side streams while the upload side buffers. Reading
  `internal/tools/get_attachment.go` shows the download side does not stream: it
  deserialises the whole attachment through the SDK (line 112), serialises it (line 132),
  and returns it base64-encoded in the tool result. **Chosen reading:** reuse
  `MaxAttachmentSizeBytes`. The asymmetry the distinct variable was justified by does not
  exist, and a second variable would add a config field, an inventory row, a
  surface-manifest entry, a docs obligation, and a second number for a user to reconcile,
  in exchange for nothing. FR-14 and NFR-6 now name the existing bound, and
  `internal/config/config.go` needs no change at all. This is the reviewer's most
  consequential call; it is reversible in one commit if a user ever needs asymmetric
  bounds.
* **Open Question 2, the upload cap value.** Follows from the above. **Chosen reading:**
  the existing default of `10485760` (10 MB), which satisfies NFR-6's requirement to sit
  well below the service's 150 MB ceiling and is already the number a user raises when an
  attachment is too large in the other direction. A consequence worth naming: the large
  path is exercisable only between 3 000 000 bytes and the cap, so at the default the
  chunked transfer covers roughly a 3 to 10 MB band unless the user raises the variable.
* **Open Question 4, the inline threshold.** The CR assumed 3 MiB (`3145728`) inclusive.
  Two properties say that is over the line, not on it: Graph states the single-`POST`
  limit in decimal megabytes rather than mebibytes, and the direct `POST` carries the
  bytes base64-encoded inside a JSON request body, expanding them by four thirds against
  Graph's request body ceiling. **Chosen reading:** route strictly below
  `3 * 1000 * 1000` bytes to the direct `POST`, and at or above it to the upload session.
  The asymmetry of the failure decides the boundary: misrouting downward fails the
  request, misrouting upward costs one extra round trip. This was not confirmed against a
  live mailbox, and a boundary test pins the intended routing rather than the service's
  actual limit.
* **The draft guard is widened rather than duplicated.** Phase 2 required the draft subject
  from the `verifyIsDraft` fetch, but the helper returns only `*mcp.CallToolResult` and
  discards the message, and neither of its two call sites was in Affected Components.
  **Chosen reading:** widen `verifyIsDraft` once, adding `subject` to its `$select` and
  returning the fetched `models.Messageable`, and update `update_draft.go:105` and
  `delete_draft.go:76` to the new signature with no behaviour change. A second copy of the
  guard would put the not-a-draft refusal string in two places, which is the instance-level
  remedy `CLAUDE.md` already records as failing to close a class. The cost is that this CR
  now touches two files it did not claim, both added to Affected Components and to Phase 1.
* **A third confirmation formatter, not an extension of the second.** CR-0078 introduced
  `FormatMailWriteConfirmation`, which carries exactly one field-and-value pair, and its
  review recorded that a verb needing two fields extends that signature rather than getting
  its own formatter. `add_attachment` reports four (attachment name, size, attachment id,
  transfer path). **Chosen reading:** a dedicated `attachment_confirmation.go`, as the CR
  proposed, but re-justified against `FormatMailWriteConfirmation` rather than against
  `FormatDraftConfirmation`, and required to follow the established line order. Four
  positional pairs is past where the shared signature stays readable.
* **The large path reads its attachment id from the `Location` header.** Phase 3 said only
  "read the created attachment id from the final chunk's response", which does not name a
  channel, and FR-10 requires the id to come from the response rather than the arguments.
  **Chosen reading:** take it from the completion response's `Location` header, falling
  back to the response body only where the service returns one, and treat a final response
  carrying no identifier as a failure rather than a confirmation naming nothing. This is
  the one contract element in the CR not confirmed against the pinned SDK, because the
  chunk `PUT` is raw HTTP outside the request-builder chain; the implementor should
  verify it against a live session before trusting the test's canned response.
* **The concepts gating row gets a gate, and one file beyond the CR's original scope.**
  `docs/concepts.md` and `docs/troubleshooting.md` were in Affected Components with no
  requirement and no acceptance criterion. **Chosen reading:** add FR-24 and AC-19, and add
  the assertion to `internal/docs/catalog_test.go` against the embedded bundle rather than
  the file on disk, following exactly the precedent CR-0078 set for the same row. The row
  must keep every string `TestMailGatingRowNamesMessageManagement` already asserts.
* **The domain introduction gets a derived check.** FR-17 had neither an acceptance
  criterion nor a test, and `TestMailDescriptionMentionsGatedVerbs` asserts only that the
  gating keys are named, not the verbs. **Chosen reading:** add
  `TestMailIntroNamesEveryGatedWriteVerb`, deriving its cases from the registry the way
  `TestManifestDescribesEveryRegisteredVerb` does, so a future gated verb added without an
  `Intro` edit fails the build. This is a small scope addition over the CR as authored, and
  it is the derive-the-cases remedy this project prefers over per-instance correction.
* **The harness step attaches to a draft the harness owns.** FR-20 did not say what to
  attach to, and the verb refuses a non-draft. **Chosen reading:** Step 41 creates its own
  draft, attaches to it, and deletes it, mirroring how CR-0078's Step 40 handled the
  non-restorable move. Appended as Step 41 without renumbering, because the historical rows
  in `docs/bench/crud-runs.csv` reference the current numbering.
* **Target version 0.11.0 left as a placeholder.** The latest release tag is `v0.6.0` and
  CR-0078 carries 0.10.0 on the same branch, so both are forward placeholders.
  **Chosen reading:** leave it and reconcile at release-planning time, matching CR-0078,
  rather than invent a number here.
* **Still outstanding, and the user's to make: the live-mailbox acceptance run.** The CR's
  Verification Commands require a user scenario driving the built server against a live
  mailbox (small file through the direct path, larger file through the session path, both
  confirmed via `list_attachments`) plus a `make crud-test` run. Neither can be performed
  during review. The large path in particular has no in-process substitute for the
  service's real chunk-completion response, which is where the `Location`-header decision
  above is confirmed or falsified.
